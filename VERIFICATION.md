## Rule-preservation review

A separate reviewer first inventoried the full versions' decision-changing rules, then compared the shortened entrypoints and references with frozen originals. Scope included:

- Selective delegation, actual runtime limits, direct fallback, leaf ownership, specialist/project routing, and authorization boundaries.
- Task versus acceptance states; inspected/current evidence, usable pointers, prerequisite exit checks, and integrated-artifact acceptance.
- Mutable-resource ownership, collection/confirmed cancellation, partial edits, safe retry/transfer, independent branches, and changed-input propagation.
- Meaningful checkpoints, hard limits versus soft guides, observable usage, preserved scope/checks, and cause-based recovery.
- Independent reviewer versus independent evidence/method versus producer self-check, proportionate integration checks, and truthful final claims.
- Proportionate run records, privacy boundaries, and separate new problem-specific skill proposals with parameterization, overlap checks, maturity/authorization limits, and distinct/boundary-case validation.

The review caught and corrected two material changes in the first orchestrate draft: omission of the prohibition on creating a user-level instruction file, and a blanket shutdown formulation stronger than the original collection-or-cancellation rule. Stopped operations/partial-change inspection before retry was also made explicit. The reviewer inspected the corrected file and confirmed resolution without additional material regressions. No material losses were found in the shortened swarm bodies or references.

Names, discovery descriptions, orchestrate UI metadata/invocation policy, design reference, and both swarm runtime adapters are unchanged. All original optional YAML example field paths and state vocabulary remain available; two task/run-record example fields were made explicit without removing existing fields. The portable plugin version advances from 1.0.0 to 1.0.1; its other metadata and marketplace example are unchanged.

## Behavioral checks

Fresh worker contexts received only the relevant shortened skill, supplied fictional inputs, and bounded permissions. They did not read producer plans, the baseline evaluations, or expected answers. The coordinator inspected their actual outputs and created artifacts.

### Orchestrate

1. A stale worker recommendation and completed task state did not establish acceptance. Current records selected Maple and rejected Cedar's insufficient current capacity. No unnecessary four-worker search was commissioned.
2. An unconfirmed stop and inaccessible extraction blocked a second editor/dependent report, while unrelated read-only work could continue. Fictional controls were not claimed as executed.
3. An exhausted verification allowance preserved missing access evidence despite repeated unsupported all-pass summaries; no compliant room was invented.
4. Agreement on an incorrect aggregate was rejected: supplied inputs yielded 32, not 36. Direct calculation and unavailable independent agent verification were distinguished. Editorial authority was not mistaken for factual verification.
5. After the focused corrections, separate boundary checks confirmed that collected/accepted idle workers need not be closed, active operations/partial edits must be resolved before retry or transfer, and unsolicited global instruction-file creation remains prohibited.

### Swarm learning

The shortened ChatGPT edition executed sequentially in a target scenario without native delegation. It selected Maple from current evidence, created a **separate** task-local `mandatory-room-selection` skill draft and `proposed_new_skills` record, then directly applied that draft to a distinct case (Ash qualified at exact capacity; Pine exceeded budget) and a boundary case (Birch lacked confirmed access, so no supported selection).

The coordinator read the actual draft and evaluation and ran the standard skill validator on the draft. Parameters, source/version checks, limits, outputs, recovery, maturity, and non-installation status were retained. Outcomes matched the critical decisions observed in the earlier full-version exercises. A separate exercise inside a real ChatGPT account or a live Claude Code runtime was not performed; both swarm editions' shared procedure and references were checked for equality.

## Second audit requested by the user

A fresh reviewer independently compared the full baselines with the corrected shortened orchestrate, both swarm runtimes, both references, and the self-contained conversation file. The reviewer did not read prior review outputs or producer plans. No material semantic regression was found. It also confirmed that the shortened proposal wording still permits a proposal/validation plan before unperformed checks, retaining draft maturity rather than demanding all validation before proposing a candidate.

A separate fresh evaluator applied both shortened workflows to five new fictional edge cases:

1. Superseded/inaccessible numerical extraction blocked dependent drafting while checked terminology work remained usable; only affected acceptance was reopened.
2. Accepted prerequisite output allowed ready formatting without closing an idle producer or waiting for an unrelated review barrier; final acceptance still required the actual review. A failed review with a live child operation required shutdown/partial-change inspection before retry or transfer.
3. A punctuation-only finance edit used direct specialist execution and proportionate inspection, without unnecessary agents, graph, financial review, approval pause, or checkpoint stop.
4. Shared-source model agreement and a document's editorial authority did not establish factual verification; unavailable required checks remained explicit.
5. A verified narrow subworkflow from an otherwise blocked task supported only a bounded learning candidate. Unknown skill overlap, privacy, remaining allowance, maturity, distinct/boundary validation, already authorized drafting, and unapproved installation were kept separate.

The evaluator found the two skills' coordination decisions consistent while preserving their intended difference: swarm includes the new-skill learning procedure; orchestrate does not add that requirement. These were read-only applications of the instructions, not actual controls on fictional workers or live product execution.
